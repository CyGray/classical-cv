## 1. LBPH `tau_accept`: 70.6089 → 67.0084

### 1.1 What changed and why

Earlier in this session, a fresh LBPH-only (no SFace, no hybrid gate)
independence test was run against **LFW1** (`data/lfw-dataset`, the raw
5,749-identity set) to answer a specific question: the unidirectional
(A→B only, upper-triangle, never B→A) impostor-distance threshold at the
165th-smallest unique cross-identity pair (~10 ppm FAR).

Two numbers came out of that, on two different scales:

1. `src/independence_common.py`'s hand-rolled chi-square reimplementation:
   raw threshold **16.7521** (`reports/independence/lbph_lfw1/summary.json`,
   `error_pair_thresholds.spec`, `error_pair_rank: 330` — ordered-space rank
   330 = unidirectional unique rank 165 via `ceil(330/2)`).
2. The **native** `cv.face.LBPHFaceRecognizer::predict_collect()` scale (the
   same scale the recognizer actually runs on in production, and the same
   scale the previous frozen `tau_accept` = 70.6089 was measured on): raw
   threshold **67.0084**
   (`reports/independence/lbph_lfw1/native_predict_scale.json`, generated by
   the new `scripts/archive/run_lfw_lbph_native_predict_independence.py`).

`docs/READ THIS/FROZEN_THRESHOLDS.md` already documented that these two scales
are non-comparable (this is exactly why `scripts/archive/build_independence_native_predict.py`
exists for Eigen/Fisher). **67.0084 (native scale) is the number that was
frozen into `tau_accept`, not 16.7521.**

Both scales agree on which pair sits at that boundary
(`Azra_Akin` vs `Mariangel_Ruiz_Torrealba`), which is a useful cross-check
that the rank/ordering logic is consistent between the two implementations
even though the distance magnitudes are not comparable.

### 1.2 Run details

- Dataset: `data/lfw-dataset` (LFW1, raw, single image per identity), no
  `--max-identities` cap.
- 5,703 of 5,749 identities kept (46 skipped — no face found by the Haar
  cascade at `--min-face-size 40`; this pipeline's Haar pass is slightly
  stricter than whatever produced the old `reports/independence/lbph_lfw1`
  legacy artifact, which reported 0 skips on a different machine's run — not
  investigated further, noted for anyone who re-runs this and gets a
  different N).
- Unique (unidirectional) pairs: 16,259,253.
- Rank 165 (1-indexed into the ascending sorted unique-pair distances) →
  realized FAR = 10.15 ppm (target was 10 ppm).
- Recognizer params: `cv.face.LBPHFaceRecognizer_create(radius=1, neighbors=8,
  grid_x=8, grid_y=8)` — identical params to `src/hybrid/independence_test.py`'s
  LBPH setup, so the number is on the same scale the deployed gate consumes.
- Runtime: ~13 minutes single-threaded (5,703 `predict_collect()` calls,
  each O(N) in OpenCV's C++ implementation — not parallelized; a 300-identity
  and 2,000-identity timing probe were used to extrapolate before committing
  to the full run).

### 1.3 New scripts added this session (not previously in the repo)

- `scripts/archive/run_lfw_lbph_streaming_independence.py` — LFW-style probe loading

## 2. SFace `l2_genuine`: 1.106796 → 1.018

Set to **1.018** on explicit instruction: this value was produced by the
SFace sub-team, not re-derived in this repo. No independence test, script, or
distance distribution in this repo was used to validate or reproduce it — it
is trusted as supplied, the same way the previous value (1.106796) was
originally hardcoded by instruction rather than derived (see
`FROZEN_THRESHOLDS.md`'s existing note that the LS-DB1 rank-8 rule does not
reproduce 1.106796 either). If the SFace sub-team's derivation method or
dataset matters for the paper's methodology section, that provenance needs to
be requested from them directly — it wasn't part of this update.

## 3. Consequences worth flagging

1. **Escalation band reopens.** `docs/audits/STATE-07-21.md` §7 found the
   LFW1-diagnostic `tau_accept` (81.04, a different partial/375-identity
   measurement) sat *above* `tau_reject` (76.85), so the hybrid cascade's
   escalation band was empty on LFW and it collapsed to LBPH-only. The new
   `tau_accept` (67.0084) sits *below* `tau_reject`, reopening a normal
   `[67.0084, 76.85]` escalation band. Anything downstream that assumed
   "LFW collapses to LBPH-only" (e.g. reasoning built on STATE-07-21 §7)
   needs re-checking against the new numbers before being cited again.
2. **`tau_accept` no longer follows the "frozen on La Salle DB1 only" rule**
   stated elsewhere in AGENTS.md and `FROZEN_THRESHOLDS.md`. Both docs were
   updated in this same change to state the new protocol rather than leave a
   contradiction; if this was meant to be a one-off exception rather than a
   permanent protocol change, someone should revert AGENTS.md's wording
   accordingly.
3. **Nothing that consumes `thresholds.json` or the two Python constants was
   re-run** after this change (no `calibrate.py` re-run, no evidence-matrix
   SHA-256 refresh, no benchmark re-run). `reports/benchmark/tar_at_far.md`,
   `reports/benchmark/lfw2_threshold_sweep_settings.csv`, and other historical
   report artifacts still contain the *old* 70.6089/1.106796 numbers — those
   are historical run records and were deliberately left untouched, but any
   *new* benchmark run will now use 67.0084/1.018 and will not be directly
   comparable to those older report rows without accounting for the threshold
   change.
